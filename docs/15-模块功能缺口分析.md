## 二、逐模块缺口

### M1 采集 🟢→ 需要增强

| 缺口 | 优先级 | 说明 |
|---|---|---|
| **定时采集** | 🔴 高 | 现在只能手动点。应加定时任务（APScheduler），按周期自动跑 |
| 源健康监控 | 🟡 中 | 源会失效（已实测 ELLE/穿针引线失效）。应有失效检测与告警 |
| **对标库** | 🔴 高 | GitHub 同类项目都有「对标数据库」。我们只有 RSS 素材，缺竞品爆款参照 |
| 增量采集 | 🟢 低 | 目前全量抓，靠指纹去重凑合 |

### M2 选题转换 🟡 需要增强

| 缺口 | 优先级 | 说明 |
|---|---|---|
| **长尾词质量过滤** | 🔴 高 | **实测出垃圾词**（"天高速公路新"、"月广州海关监"）。需要过滤：太短、太泛、含数字乱串、跨词断裂 |
| 选题去重/相似合并 | 🟡 中 | 同一事件多次采集会产生近似选题 |
| 关键词分类打标 | 🟢 低 | 便于按类型筛选 |

### M3 稿件 🟢→ 需要增强

| 缺口 | 优先级 | 说明 |
|---|---|---|
| **技能库（SOP）** | 🔴 高 | GitHub 同类项目的核心做法：把「怎么写标题」「怎么开头」做成技能让 Agent 加载。我们还没 |
| **去 AI 味** | 🔴 高 | 平台对 AI 味敏感。需口语化改写 + 人味细节注入 |
| 标题候选生成 | 🟡 中 | 现在只预填长尾词，应出 3-5 个候选供选 |
| 版本历史 | 🟢 低 | 改坏了要能回退 |

## 三、★ 核心：Agent 应该能「改」工作台

### 王哥的原话

> 「接入的 harness 的才是灵魂，重点不合适的是**可以让 harness 修改**，这才是灵活的，更方便」

### 现有架构的问题

```
现在：Agent → 只能调我预置的 4 个界面能力（切页签/筛选/开选题/读状态）
问题：想要新能力 → 我改代码 → 前端重新构建 → 等编译
```

**这违背了 hbridge 的设计初衷**。v2.1 的核心是「**执行体留在客户端，模型调用推回浏览器执行**」——能力应该是**运行时可注册**的，而不是编译期固化的。

### 应该怎么做

hbridge 提供了 `bridge.register(capabilities)`，可以**运行时动态注册能力**。所以：

| 层级 | 能力 | 谁定义 |
|---|---|---|
| L1 | 基础原子操作（DOM/导航/表单/状态）| 内置，我提供 |
| L2 | **业务能力** | Agent 运行时注册 |
| L3 | **界面结构** | Agent 运行时组织 |

举例：
- 用户说「加一个对比表格页」→ Agent 调 `ui_add_panel`，传页面配置 → **不用改代码**
- 用户说「给选题加个优先级字段」→ Agent 调 `schema_extend` → 动态扩展
- 用户说「按我的口径重新定义爆款」→ Agent 注册一个 `judge_viral` 能力 → **把王哥的经验变成工具**

### 设计原则

1. **原子能力我做，组合能力 Agent 给** —— 我提供积木，Agent 盖房子
2. **不改代码就能加功能** —— 热注册，热生效
3. **持久化** —— Agent 注册的能力存到 localStorage/后端，下次还在
4. **可审计** —— 注册了什么要能查、能删

## 四、补全优先级建议

```
P0（核心）★ Agent 自改工作台机制
P1  定时任务（采集+快照）· 长尾词质量过滤 · 去AI味 · 接真实生图
P2  技能库（SOP）· 对标库 · 发布包导出 · 官方数据接入
P3  标题候选 · 版本历史 · 趋势图 · 通知
```

**先做 P0**，因为它会改变后续所有功能的设计方式——有了它，很多缺口 Agent 自己就能补。
