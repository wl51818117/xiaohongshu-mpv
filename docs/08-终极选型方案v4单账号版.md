## 一、单账号约束带来的架构简化（重要）

王哥确认只有 1 个号，这**直接砍掉了一大块复杂度**：

| 原设计（多账号）| 单账号简化版 | 变化 |
|---|---|---|
| 账号矩阵管理（主号+子号关联） | **删除** | 不需要 |
| 3 个子账号红线防护 | **不需要** | 绕开 |
| 跨账号差异化生成 N 份 | **删除** | 不需要 |
| 多账号发布节奏分散（20-90min随机） | **不需要** | 单号无关联判定 |
| 登录态按用户隔离、多账号切换 | **一个登录态即可** | 简化 |
| 60% 跨账号相似度判定 | **仍需注意**（同号重复发布） | 保留 |

**但仍需守的底线**：
- ✅ **同账号内不要重复发高度相似的内容**（自我重复也算低质）
- ✅ **相似度 60% 仍是平台判定线**
- ✅ 平台 2026 处置了**超百万例** AI 不良行为，AI 托管账号 80 万+

**结论**：系统可以专注做「**一个号的精品内容生产线**」，把复杂度让给内容质量本身。这是好事。

## 二、⭐ 最重要的发现：Beav 的 Plugin 是一个现成的浏览器控制 MCP

我读了 `Plugin/mcp-server.mjs` 和 `.mcp.json` 的源码，**这是本次调研最有价值的东西**。

### 2.1 它是什么

一个 **60+ 工具的浏览器控制 MCP Server**，通过 JSON-RPC over stdio 通信：

```js
// Plugin/mcp-server.mjs 核心
FALLBACK_TOOLS = [
  'browser.capabilities', 'browser.info',
  'research.run',                    // ★ 有界只读站点调研，带 DOM 证据
  'tab.claim', 'tab.create', 'tab.navigate',
  'page.domSnapshot',                // ★ DOM 快照
  'page.queryElements', 'page.click', 'page.type',
  'page.screenshot', 'page.assets',// ★ 截图 + 资源清单
  'clipboard.readText', 'clipboard.writeText',
  'input.mouseClick', 'input.keyboardType',   // ★ 真实鼠标键盘输入
  'cdp.send',                        // ★ Chrome DevTools Protocol 直发
  'browser.botDetect',               // ★ 检测登录/验证码/风控拦截
  'browser.authHandoff',             // ★★ 交还人工登录，返回结构化等待状态
]
```

### 2.2 两个设计直接命中我们的痛点

#### ⭐⭐ `browser.authHandoff` —— 解决「登录必须人工」

```js
browserTool('browser.authHandoff',
  'Retain one controlled tab for manual login or verification, then return a typed waiting_for_user result.',
  { tabId: {...}, reason: { enum: ['login_required',
      'security_verification_required',
      'bot_verification_required'] }, ttlMs: {...} })
```

**这是完美的登录处理**：
- 检测到需要登录/验证码时，**把标签页交还给人工**
- 返回**结构化的 `waiting_for_user` 状态**，而不是硬失败或硬闯
- 原因分类明确：`login_required` / `security_verification_required` / `bot_verification_required`

→ **正好对上我们 harness 的 approval 机制**：内核遇审批会 waterfall 出 `approval/request`，我们把 `authHandoff` 的等待态映射成审批请求即可。

#### ⭐ `browser.botDetect` —— 风控感知

```js
browserTool('browser.botDetect',
  'Detect a visible login, CAPTCHA, or security-verification blocker without reading credentials.', ...)
```

**在动页面之前先探测有没有风控拦截**，这比事后补救强得多。配合之前调研到的「风控是事后聚类、有行为指纹」结论——**能提前知道被拦，就不要继续自动化操作**。

### 2.3 ⚠️ 但它的输入方式是 stdio，不是 streamable-http

```json
// Plugin/.mcp.json
"browser-control": {
  "type": "stdio",
  "command": "node",
  "args": ["./mcp-server.mjs"]
}
```

**好消息**：我们 harness 的 `dsh-mcp-client` **支持 stdio 模式**（01 号文档已验证）：
```yaml
- insert:
    - id: mcp-browser
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        transport: stdio
        serverName: browser
        command: node
        args: ['E:/.../mcp-server.mjs']
        toolCallTimeoutMs: 60000
```

→ **Beav 的 Plugin 可以直接挂进我们的内核**，工具会以 `mcp__browser__*` 形式出现。

### 2.4 ⚠️⚠️ 许可证是硬约束（必须先解决）

我读了 `Plugin/LICENSE` 原文：

```
MIT License – Non-Commercial Use Only
Permission is hereby granted... to deal in the Software without restriction...
**for non-commercial purposes only**
**Commercial use of the Software is strictly prohibited without prior written permission from the author.**
```

**结论**：
| 用途 | 可行性 |
|---|---|
| **读源码学习设计思路** | ✅ 完全可行（著作权允许阅读研究）|
| **Fork 改造后内部自用** | 🟡 可行（不构成分发）|
| **集成进我们的闭源工作台** | 🔴 **不可行**（未获作者书面授权）|

**王哥说「beav 的代码是要参考的」——这个方向完全正确，而且必须严格停留在「参考」层面**。

**具体做法（合法且有效）**：
1. **学习它的架构设计**（尤其是 authHandoff / botDetect 的设计模式）
2. **自己实现同等功能**（我们的代码是独立作品，不复制它的源码）
3. **保留设计出处注释**（注明参考自Beav 的哪个机制，这是业界通行做法）

⚠️ 这一点必须在开工前跟王哥讲清楚，避免未来商业化时埋雷。

## 四、借鉴 Beav 的三个核心设计

### 4.1 authHandoff 模式（最值得抄的设计）

**Beav 的做法**：遇登录/验证码 → 交还标签页 + 返回 `waiting_for_user` 结构化状态

**我们照做**：
```
浏览器控制工具调用 → 检测到登录页/验证码
   ↓
内核 approval/request waterfall（复用 harness 现成机制）
   ↓
SSE 推给前端 → 前端弹出「请人工登录」卡片
   ↓
用户在浏览器里完成登录（扫码/验证码）
   ↓
点「已完成」→ 回POST /v1/approve → 内核继续
```

**收益**：不需要自己设计一套登录等待态，直接映射到内核已有的审批闸门。

### 4.2 botDetect 前置探测

**Beav 的做法**：动页面之前先探测有无风控拦截

**我们照做**：发布前先探测 → 若命中风控，**停止自动化，转人工**，不做无谓尝试。

### 4.3 分级审批模式（.mcp.json 里的设计）

Beav 对每个工具单独配 `approvalMode`（`never` / `destructive`）：
```json
"perTool": {
  "page.screenshot":    { "approvalMode": "never" },
  "page.click":         { "approvalMode": "destructive" },
  "page.type":          { "approvalMode": "destructive" },
  "clipboard.readText": { "approvalMode": "destructive" }
}
```

**这是个好设计**：读操作免审批，写操作需审批。
→ 我们的 `xhs_*` 工具也该这样分级：
- 读取类（`xhs_list_topics`、`xhs_fetch_hot_topics`）→ 免审批
- 写入类（`xhs_claim_topic`、`xhs_build_post`）→ 需审批
- 发布类（`xhs_publish_draft`）→ **必须审批 + 人工确认**

## 五、单账号版的内容生产流程

```
┌─ 采集层（三源）──────────────────────────┐
│ RSS 源（王哥已有）                        │
│ 自有爆款回采（XHS-Downloader MCP）        │
└──────────────┬──────────────────────────┘
               ↓
      统一素材库（标 own_flag）
               ↓
   AI 二次创作（四条差异化规则，至少三条）
   ⚠️ 单账号也要防自我重复：同主题不重复发
               ↓
        选题库 topics
               ↓
   文案工坊（生成 → 去 AI 味 → 合规校验）
               ↓
        素材生产
   ├─ 图文：guizang 卡片渲染（主力）+ AI 生图
   └─ 视频：首帧图 → 图生视频 → ffmpeg
               ↓
        组合发布包（AI 声明必填）
               ↓
   ┌────────────────────────────────────┐
   │ botDetect 探测 → 无风控才继续        │
   │   ↓                                │
   │ 自动预填 → botDetect 复检            │
   │   ↓命中风控则停下                   │
   │ 【人工点发布】                       │
   └────────────────────────────────────┘
               ↓
        数据回流（1/3/7/14 天快照）
               ↓
        爆文要素 → 回流选题库
```

**单账号的简化点**：
- ✅ 无需账号矩阵管理
- ✅ 无需跨账号差异化N 份
- ✅ 无需发布节奏分散
- ⚠️ **仍需**：「同主题不重复」「60% 相似度自查」「AI 声明必标」

## 七、开工前必须明确的三个问题

| # | 问题 | 为什么关键 |
|---|---|---|
| 1 | **Beav 的「参考」边界** | 它是 MIT 非商用。我们可读源码学设计、自建实现，**但不能复制代码进我们的工作台**。如果未来要商业化，这条必须提前定好 |
| 2 | **单账号的赛道/定位是什么？** | 决定 RSS 源清单、AI 选题转换规则、素材风格。内衣电商？泛生活？|
| 3 | **是纯自用还是要做成产品？** | 纯自用则许可证约束宽松；若要做成产品对外，则 guizang（AGPL）和 Beav（非商用）都不能集成，只能独立调用 |

**我的建议**：先按**纯自用**做，把架构留好扩展余地。这样最快能用起来，也不踩任何许可证坑。
