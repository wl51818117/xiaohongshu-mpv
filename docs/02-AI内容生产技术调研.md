## 摘要：三个必须先知道的结论

在展开细节前，有三个结论会直接改变系统设计，必须先说：

### 结论 1：小红书开放平台**没有**面向普通开发者的笔记发布 API

我直接读取了小红书官方 API 文档站（xiaohongshu.apifox.cn）的应用类目说明。**当前全部 6 个应用类目都是电商类**：

| 类目 | 面向 | 授予的 API 权限 |
|---|---|---|
| 一键搬家 | 第三方/商家 | 公共、授权、商品、库存、素材中心 |
| 商品优化 | 第三方/商家 | 公共、授权、商品、库存、素材中心 |
| 商品打单工具 | 第三方/商家 | 公共、授权、商品、订单、售后、库存 |
| 订单管理 | 第三方/商家 | 公共、授权、商品、订单、售后、库存、素材中心 |
| 企业 ERP / 跨境 ERP | 第三方/商家 | 公共、授权、商品、订单、售后、库存、素材中心 |
| 商家后台系统 | **商家自研** | 所有权限包 |

**关键观察**：类目里出现的"素材中心接口"是**商品主图/视频素材**，不是笔记图文内容。文档中**不存在**"笔记发布""内容发布""笔记数据查询"类目。

> ⚠️ 网上大量教程（含 CSDN、掘金等）声称"申请笔记发布接口，POST /posts/publish"，并给出伪造的代码。经核对官方文档，**这些接口在公开文档中不存在**。这类内容多为 SEO 农场或第三方 reseller 的引流文，**不要采信**。

**推论**：任何号称"官方 API 一键发布小红书"的服务，要么是伪造文档，要么是包装了浏览器自动化/逆向抓包。**系统设计不能把它当作可用依赖。**

### 结论 2：全托管 AI 代发是官方明确打击对象（这是硬约束，不是风险提示）

2026 年 3 月 10 日，小红书「薯管家」发布公告（IT之家当日转载），明确治理 AI 托管账号。**我已抓取该公告原文核对**，分级处理如下：

> 「近期，平台发现部分用户采用 AI 托管模式运营账号，通过技术手段自动生成内容、发布笔记，并在评论、私信、群聊等场景中模拟真人互动。……即日起，平台将对 AI 托管类账号实行以下治理措施：
>
> 1、对于普通账号**偶发使用 AI 托管代写、代发笔记**或进行互动，平台将根据违规程度，采取**警告、限制内容分发等梯度处理措施**。
>
> 2、对于**直接通过 AI 托管工具注册、发布、互动的账号，或主页所有公开笔记均为 AI 托管代发的账号，平台将予以封禁处理**。」

配套的《小红书社区规范》4.4.3 点名「**非正常模式地发布笔记，如批量发布、高频发布、机器发布等**」，4.4.4 点名「通过程序、脚本模拟……产生虚假数据」。认定标准只有两条：人工排查，以及「**小红书算法系统对一定周期内的数据进行排查后，抓取到异常数据的**」。

**推论**：这条直接否决了"全自动无人值守发布"的产品形态。系统的终态必须是 **人机协作**——AI 负责生产，人负责审核与发布决策。见 §C 推荐路线。

### 结论 3：抖音/微信生态的"官方发布"通道小红书没有对标物，必须自建或用第三方

这不是缺陷而是事实：内容工作台类产品的通用做法是接第三方多平台发布 SaaS（媒想到、新媒体管家、蚁小二等），它们通过模拟操作或渠道代理实现，**合规边界由平台方裁定，工具方不提供保证**。这一点必须写进产品的风险披露里。

### A.2 角色/模特一致性：分层方案（这是电商内容的核心难点）

小红书电商内容天然要求「同一位模特出镜」——这是**虚拟模特/AI 模特带货**的技术底座。按可靠性从低到高：

#### 方案 1：Seed 控制（免费，仅适合同构图微调）
同 prompt + 同 seed → 相似输出。**一旦场景变化（咖啡店→海边）人脸就漂移**。定位是"微调旋钮"，不是身份方案。

#### 方案 2：参考图 / 多图参考（推荐主力，性价比最高）
- **Nano Banana 2**：支持最多 10 个物体参考，Google 明确建议「include previously generated images」来维持一致性。
- **Nano Banana Pro**：支持最多 **5 个人物参考** + 14 图融合，适合"同一人多场景"。
- **Seedream 4.0/4.5**：原生支持多图参考，中文提示词 + 参考图组合效果好，是国内 API 里最省事的选择。
- **Midjourney**：`--cref`（角色参考）+ `--sref`（风格参考）组合，是目前**一致性最高的 C 端方案**，但无 API。

**素材准备规范**（工程上必须固化，否则一致性必崩）：
- 8–15 张"标准参考集"：正面、3/4 侧、纯侧面、2–3 张不同光照、2–3 张不同表情、可选一张全身。
- 统一服装（或刻意极简）、统一背景（纯色影棚背景最佳）、统一画风、全高清锐利。
- 一次性批量生成 30–50 张后**人工精选**，丢弃手部畸形/眼距不对的——**这些瑕疵会被模型吸收进身份特征并永久复现**。

#### 方案 3：LoRA 训练（金标准，商用推荐）
- 数据：20–50 张精选图，裁剪到 512×512 或 1024×1024。
- 训练：kohya_ss，**1000–3000 步**（单角色 1500–3000 足够，过多会过拟合参考背景），LR 1e-4，network rank 32 / alpha 16，**RTX 3090 上 15–25 分钟**。
- 触发词：`ohwx woman` 之类的唯一 token，caption 保持极简——**让 trigger 吸收身份，而不是吸收场景**。
- 产出：50–200MB LoRA 文件，可挂载在任何 SD/Flux 基座上，快速换角色。
- 成本：**Replicate 上 $2–$10/次训练**。
- 留出 2–3 张参考图做泛化测试（验证模型是"学会"了而不是"记住"了）。
- ⚠️ Google 官方模型卡明确写着 **"Character consistency is not always perfect between input images and generated output image"** —— 即使用 Nano Banana Pro，也不要假设 100% 一致。

#### 方案 4：人脸修复（兜底，不是主方案）
ReActor（SD 扩展）/ InsightFace 换脸。**永远能出一致的脸，但脖子/下颌线会露出不自然痕迹**。只在其他都对、脸不对时用。

#### 方案 5：姿态/结构控制（与身份层解耦）
ControlNet（pose/depth/canny）控制身体姿态，让身份层只管脸。**关键技巧**：先用占位人物生成姿态构图，再叠加角色 LoRA 重绘——这样模型不会为了"解 pose"而牺牲面部相似度。

**一致性能力分层**（业界共识）：
```
seed 控制   → 弱（同一 vibe，非同一张脸）→ 1–3 张图
参考图      → 强（4–15 张图可识别同一身份）→ 日常电商内容主力
LoRA 训练   → 接近完美（任意场景同一张脸）→ 长期 campaign、品牌吉祥物
参考图+LoRA → 最强（同时锁身份与姿态）→ 商业交付级
```

### B.2 图生视频路径选型（与"AI生图+AI生视频"串联工作流强相关）

**这是本系统的核心链路：AI 生成的静态封面/模特图 → 动态短视频。** 按"图生视频"专项能力排序：

**第一梯队 —— 图生视频 + 首尾帧双支持，且价格可接受**
- **Seedance 2.0 / 2.0-mini**：国内首选。mini 720P 2.48 元/5 秒，支持首尾帧 + 图生视频 + 参考图（最多 30 张参考图）。**中文提示词 + 竖版适配好 + 国内 API 稳定**。

### B.3 小红书竖屏短视频（9:16、15–60 秒）对生成的硬要求

| 要求 | 数值 | 说明 |
|---|---|---|
| 画幅 | **9:16** | Seedance / Kling / Vidu 均支持指定宽高比 |
| 时长 | 单次生成 3–15s，**需拼接** | 小红书支持到 15 分钟，短视频最佳 15–60 秒 |
| 分辨率 | **1080P 起步**（1080×1920） | 720P 在手机上明显糊 |
| 帧率 | 24/30fps | 60fps 成本显著更高 |
| 首帧衔接 | 必须与封面图一致 | **这就是图生视频的价值**：封面即首帧 |
| 音频 | 小红书重视 | 原生音频模型（Seedance 2.5 / Kling 3.0 Turbo）成本 +50% |
| 水印 | 商用须无水印 | Seedream/Seedance/可灵付费版、Kling 免费档**带水印且不可商用** |

**工程要点**：
1. **图生视频是必选项，不是可选项**。T2V（文生视频）的画面不可控，无法保证与封面/商品图一致，电商场景不可用。
2. **60 秒需分段生成 + 拼接**。建议在系统里做「分镜表 → 逐镜图生视频 → ffmpeg 拼接 + 统一转场/字幕/BGM」的流水线。转场/字幕/音乐用 ffmpeg 解决，不依赖生成模型。
3. **首尾帧是最省事的一致性方案**：同一模特的两张图（正面/侧面）作首尾帧，模型负责中间过渡。

## C. 小红书内容发布的技术路径（重点）

### C.1 官方途径：能力边界

**入口**：`https://open.xiaohongshu.com`（文档镜像 `xiaohongshu.apifox.cn`）

| 问题 | 结论 |
|---|---|
| 平台有笔记发布接口吗？ | **公开文档中不存在**。6 个应用类目（见摘要）全部为电商类 |
| 有"素材中心接口"吗？ | 有，但作用域是**商品主图/视频素材**，非笔记内容 |
| 有"内容发布""笔记数据"类目吗？ | **没有** |
| 申请条件 | 需企业资质 + 应用审核；开发者自研"商家后台系统"类目可获所有权限包，但仍是**商家经营后台**能力，不是内容发布能力 |
| 笔记数据能拿吗？ | 商家后台可看自己店铺的笔记表现；**竞品/他人笔记数据无官方接口** |

> 网上流传的"小红书笔记发布 API"教程（含 `posts/publish`、`/oauth/token`）在官方文档中**查不到对应页面**。这类内容应视为第三方 reseller 包装，**接入即意味着账号凭证外流 + 条款风险**。

**结论：官方 API 路径对本系统不可用。** 系统必须自建发布通道或采购第三方服务。

### C.2 第三方发布工具评估

| 工具类型 | 代表 | 实现原理 | 稳定性 | 合规风险 |
|---|---|---|---|---|
| **媒体号矩阵 SaaS** | 新媒体管家、蚁小二、易媒助手、乐观号、融媒宝 | 浏览器自动化 / 桌面客户端 / 托管云端浏览器 | 🟡 中（页面改版即失效） | 🟡 中高 |
| **RPA** | 影刀 RPA、UiBot | 模拟真人操作，录制回放 | 🟢 较稳（可人工接管） | 🟡 中（仍属"机器发布"） |
| **本地部署型** | 部分工具支持本地浏览器 | 登录态留在自己机器 | 🟢 较稳 | 🟢 相对低 |
| **云端托管型** | 部分 SaaS | 账号托管给云端服务器全天代跑 | 🟡 中 | 🔴 **高**（命中公告"AI 托管"定义） |

**关键区分点**（很多工具宣传时模糊处理）：**登录态是留在你自己电脑的浏览器里，还是把账号交给云端服务器全天代跑？** 后者直接落入 2026-03 公告的封禁情形。

**工具宣传的可信度问题**：我检索到的新媒体管家/蚁小二/易媒助手/来鼓AI 等对比文章（多发布于工具自家知识库 `xueyuan.yixiaoer.cn`）**互相推荐自家产品**并给出"不易触发风控""封号概率低"等无数据支撑的结论。这些是**营销内容，不是评测**。选型应要求：书面 SLA、失败重试机制、日志可审计、不存储明文密码。

**实际单账号日发布量建议**：不超过 3–5 条，间隔 30 分钟以上（工具类文章普遍建议，与官方"高频发布"违规条款一致）。

### C.3 浏览器自动化发布（Playwright / Puppeteer / Selenium）

**技术可行性：可行，但对抗成本高且在恶化。**

**小红书已知反爬层次**（社区逆向资料汇总）：

| 层次 | 具体机制 | 应对 |
|---|---|---|
| **请求签名** | `x-s` / `x-t` / `x-s-common`，JS + Native 联合生成，绑定 cookie / URL / body / 设备指纹 | 算错直接 **461 / 406** |
| **WAF 挑战** | `acw_sc__v2`（阿里云 WAF JS 挑战 cookie） | 需执行 JS |
| **CDP 痕迹** | `Runtime.enable` 痕迹检测（Cloudflare / DataDome 同款手法） | 需规避 |
| **设备指纹** | User-Agent、Canvas 渲染哈希、WebGL 参数、字体列表；`webId` / `gid` / `a1` / `x-mini-gid` 需会话内一致 | 需固化指纹 |
| **行为指纹** | 鼠标贝塞尔曲线、点击间隔分布、滚动节奏、输入特征（真人有 typo 和 backspace） | 需节律模拟 |
| **传感器** | 移动端读陀螺仪/加速度计微抖动 | 机器人没有 |
| **关联打标** | 同设备多账号标签 | 一号一设备一 IP |
| **事后聚类** | **延迟 + 概率**的处置模型 | ⚠️ 见下 |

**最关键的一点：风控是事后聚类，不是实时拦截。**
这解释了为什么"昨天没事，今天醒来一堆账号被警告/限流"——平台采行为信号后聚类、与已知账号关联打标，**是有意设计的延迟处置**，让攻击方无法实时摸到边界。

> **推论：即使指纹伪装完美、用了真人账号、真住宅 IP，AI Agent 操控真实浏览器仍会被识别。** 反爬厂商（Cloudflare / DataDome 等）已经用 mouse dynamics 直接训分类器——AI 控制鼠标与人类的"运动神经差异"是**统计学差异**，不是任何 stealth 插件能补的。

**已知封号率参考**：有工程实践文章称其自研方案"连续发布 500 条被标记为疑似机器的比例 0.4%，远低于行业平均 12%"。⚠️ **注意：这是自述数据，无第三方验证，且分母（500条/多少账号/多少天）不明。仅作为量级参考，不作为保证。**

**逆向签名方案的额外风险**：
- 直接调用未公开接口 + 破解签名算法，**明确违反小红书服务条款**
- 签名算法随版本更新，**维护成本高、随时失效**
- 已知判例：2024 年陈某等三人**破解小红书加密算法非法获取用户数据，被判有期徒刑三年并处罚金、没收全部违法所得**

### C.4 半自动方案对比

| 方案 | 自动化程度 | 风险等级 | 适用 |
|---|---|---|---|
| **A. 人工剪贴板/文件投递** | 低（只生成素材包，人工上传） | 🟢 **低** | **推荐主路径** |
| **B. 本地浏览器扩展注入**（用户在自己浏览器点"发布"） | 中 | 🟢 低—中 | 推荐，可控性最好 |
| **C. Chrome 扩展 + 半自动填表** | 中高 | 🟡 中 | 次选 |
| **D. 桌面 RPA 客户端** | 高 | 🟡 中 | 需人工接管能力 |
| **E. 云端全自动无人值守** | 最高 | 🔴 **高（公告封禁项）** | **不建议** |
| **F. 手机/微信 RPA** | 高 | 🔴 高 | 不建议 |

**方案 A 的具体形态**（推荐）：
系统生成一个"发布包"：`标题.txt` + `正文.txt` + `话题标签.txt` + `封面.jpg` + `配图2~9.jpg` + `视频.mp4` + `一个本地 HTML 预览页`（含敏感词自检结果 + 合规自检清单）。运营人员打开网页版创作服务平台（`https://creator.xiaohongshu.com`），复制粘贴 + 上传 + 点发布。

**这个方案的价值**：它把 AI 的价值集中在"生产"环节（提效 80%+），而把"发布"环节完全留在人手里——**这正是官方公告划出的安全边界**（"偶发使用 AI 托管代写、代发"是警告/限流，"主页全部 AI 托管代发"是封禁；但"AI 帮你起草、你改过确认再发"和"完全不看就发出去"在规则里是两件事）。

### C.5 账号矩阵管理

| 做法 | 风险 |
|---|---|
| 一个主体运营一个账号 | 🟢 最安全 |
| 多账号共用同一设备/IP | 🔴 高（关联打标） |
| 多账号一号一 IP + 环境隔离 | 🟡 中（仍需各号内容/节奏不同） |
| 账号池 Cookie 集中托管在服务端 | 🔴 高（凭证风险 + 托管定义） |
| 账号买卖/租用 | 🔴 极高（可能涉及非法使用个人信息，违反《个人信息保护法》） |

**矩阵的合规前提**（缺一不可）：
1. 各账号**内容互不相同、节奏互不同步**——否则构成《社区规范》4.4.2「滥用权益注册或开设多个账号」
2. 单账号发布量不超过人工能审完的量
3. 不做批量刷赞/刷评论/自动私信（4.4.4 明确禁止，公告也点名"虚假互动"）
4. 账号来源合法

| 路线 | 风险等级 | 采纳建议 |
|---|---|---|
| ~~全自动无人值守发布~~ | 🔴 **极高** | **否决**。直接命中 2026-03 公告封禁条款 |
| 半自动（本地扩展/人机协作） | 🟢 低—中 | ✅ **推荐主路径** |
| 纯人工上传 + 系统只做素材生产 | 🟢 **低** | ✅ **推荐 MVP 路径** |
| 官方 API | — | ❌ 不可用（能力不存在） |
| 逆向签名直调接口 | 🔴 高 | ❌ 明确违反条款 + 有刑事判例 |
| 自研 Playwright 全自动 | 🔴 高 | ⚠️ 若做，必须：本地运行、节律模拟、一号一环境、**发布前强制人工确认** |

**最终推荐：人机协作（Human-in-the-loop）**
```
选题 → [AI] 文案生成 → [人] 审核修改 → [AI] 配图/视频生成
     → [人] 终审 + 敏感词自检 → [人] 手动发布（系统提供发布包+预览）
     → [人] 发布后 30 分钟内浏览/回复评论（关键行为信号）
```
系统全程**不触碰发布动作**。这既符合公告边界，也规避了浏览器自动化的全部对抗成本。

**产品化建议**：在系统里内置《发布前两分钟自检清单》（见下），把合规从"事后救火"变成"事前拦截"。

> **自检清单**（任一为"是"即需整改）：
> 1. 过去 7 天发布时间是否几乎落在同一分钟？
> 2. 几个号是否经常在同一时间段集中发布？
> 3. 发布前后该号是否几乎没有浏览、点赞、回复评论的记录？
> 4. 笔记里的体验/产品/地点有没有编造的部分？
> 5. 几个号最近 5 篇标题并排看，是否一眼同模板？
> 6. 主页里是否没有一篇是你亲自改过、确认过的？
> 7. 多个号是否共用同一台设备、同一个网络出口？
> 8. 每天发布量是否超过了你能认真审完的量？
>
> 前 6 题里只要有 2 题答"是"，**先改节奏和内容，别急着换环境**——环境再干净也洗不掉行为层和内容层的问题。

### D.4 自研爬虫方案

**主流开源方案：MediaCrawler**（GitHub 约 53.9K Star）

- **覆盖**：小红书、抖音、快手、B 站、微博、贴吧、知乎（7 平台能力齐平）
- **核心巧思**：**不做 JS 逆向**。用 Playwright 启动/连接真实浏览器，在**已登录的浏览器上下文里直接执行 JS 表达式**，让浏览器自己算出签名，再把结果回传给 HTTP 层发包。代码里没有一行加密算法。
- **CDP 模式**（重要）：默认推荐连接**本机已有 Chrome**（`--remote-debugging-port`）而非启动干净 Chromium，复用现有登录态和 Cookie，比自造请求头稳得多。
- **能力矩阵**：关键词搜索、指定笔记 ID、二级评论、创作者主页批量、登录态缓存、IP 代理池、评论词云图（7 平台全支持）
- **输出格式**：CSV / JSON / JSONL / Excel / SQLite / MySQL
- **WebUI**：官方用 FastAPI 写了 Web 管理界面
- **环境**：Python 3.11+、Node.js 16+、Chrome ≥144，推荐 uv 管理依赖
- **收费版 MediaCrawlerPro**：断点续爬、多账号代理池、AI Agent 内容拆解

**运行命令示例**：
```bash
uv run main.py --platform xhs --lt qrcode --type search
```

**爬虫对抗现状**：
- 小红书的 `x-s` / `x-t` 签名算法**持续变化**，纯逆向方案维护成本高、常数失效
- **MediaCrawler 的浏览器上下文方案是目前性价比最高的路径**（"浏览器帮我们算了"）
- 风险：仍需扫码登录账号；IP 池需真实住宅代理；请求间隔需随机 2–8 秒

**对工作台的直接建议**：
> ❗ **不要自研爬虫作为产品核心能力。** 理由：① 签名对抗是持续投入的无底洞；② 账号风险直接传导到客户资产；③ 商业使用第三方数据的法律边界更清晰。
>
> ✅ 若确有需要，**采购第三方数据平台的数据 API**（千瓜/新红/灰豚多数提供开放平台/数据导出），把预算投在数据质量而非对抗上。
>
> ⚠️ 若一定要爬：**严格限制在公开数据、遵守频率限制、不采集评论中的个人信息、账号与业务账号物理隔离**。这些账号只用于采集，与发布账号完全分离。

### D.5 合规红线

**三条企业爬虫红线**（业内共识）：
1. **不违反网站 robots 协议**
2. **不侵犯数据权益**（不碰手机号、身份信息等个人信息）
3. **不影响网站正常运营**（大规模爬取导致服务器崩溃）

**公开数据 vs 非公开数据的分界**：
| 类型 | 举例 | 合法性 |
|---|---|---|
| 公开数据 | 无需登录即可访问的笔记标题、内容、互动数 | 🟢 通常合法（但需遵守 robots 与频率） |
| 半公开数据 | 需登录后才能看：私信、粉丝列表 | 🟡 需授权 |
| 私有数据 | 手机号、地址、聊天记录 | 🔴 **禁止采集** |

**法律风险（按严重程度）**：

| 风险 | 法律依据 | 后果 |
|---|---|---|
| **破解加密算法非法获取数据** | 《刑法》285 条、《网络安全法》 | ⚠️ **已有小红书判例：2024 年陈某等三人被判有期徒刑三年 + 罚金 + 没收全部违法所得** |
| 抓取含个人信息的电商用户数据 | 《个人信息保护法》 | 行政处罚 + 民事赔偿 |
| 商业使用未授权的抓取数据 | 《反不正当竞争法》 | 侵权赔偿 |
| 爬取他人图片/文章商用 | 著作权 / 商标权侵权 | 赔偿 + 下架 |
| 绕过反爬机制（验证码/IP限制） | 可能构成「非法侵入计算机信息系统」 | 行政或刑事责任 |
| 抓取不致瘫痪但高频请求 | 《反不正当竞争法》 | 可能构成"妨碍正常运营" |

**参考判例**：
- 2023 年柯某爬取腾讯、优酷等平台 5 万余部视听作品并传播 → **判刑三年 + 罚金 40 万**
- 2024 年陈某等三人**破解小红书加密算法**非法获取用户数据 → **判刑三年 + 罚金 + 没收违法所得**

**商用场景的可行边界**：
| 用途 | 可行性 |
|---|---|
| 自有账号数据复盘 | 🟢 完全可行（官方导出） |
| 行业趋势研究（公开数据、聚合统计） | 🟡 可行（数据服务商采购） |
| 竞品选题参考（不落地原文） | 🟡 谨慎可行 |
| 抓取原文/图片直接发布或改写 | 🔴 **不可行**（著作权） |
| 采集用户评论做训练语料 | 🔴 **不可行**（个人信息 + 著作权） |
| 破解签名/加密接口 | 🔴 **不可行，有刑事判例** |

**合规建设清单**：
1. 查 robots.txt
2. 明确数据性质，不碰非公开数据
3. 留存授权文件（第三方数据服务的合同是重要护身符）
4. 控制频率，不妨碍目标网站
5. **每季度做一次合规审计**
6. 数据脱敏处理
7. 数据留存期限不超必要期限，到期删除

## E. 参考技术栈建议

### E.1 推荐组合（一句话版）

```
前端：Vite 6 + React 19 + TypeScript + Tailwind CSS 4 + TanStack Query
后端：FastAPI（Python 3.12）+ SQLAlchemy 2 + Alembic
数据库：PostgreSQL 16（主）+ Redis 7（缓存/队列）
任务队列：Redis + arq / RQ（初期）→ Temporal（规模化后）
对象存储：腾讯云 COS 或 阿里云 OSS（国内，对象存储+CDN 一体）
```

### E.2 选型对比与理由

#### 前端：Vite vs Next.js

| 维度 | Next.js 16 | Vite 6 + React 19 |
|---|---|---|
| 定位 | 全栈 meta-framework | 纯客户端 SPA |
| 优势 | SSR/SEO、Server Components、Server Actions 省掉一层 API | 静态文件部署、无前端服务器、架构心智负担低 |
| 劣势 | 缓存模型与服务端/客户端边界学习成本高；**有不可逆性** | 需自选路由/数据层 |
| 安全面 | 前端服务器执行服务端代码，**要按后端节奏打补丁** | 纯静态文件，安全在 API 侧 |

**推荐 Vite + React。理由**：
1. 这是**登录后的内部工作台**，SEO 收益为零，SSR 是纯开销
2. Next.js 的 RSC/Server Actions 边界**迁移成本不可逆**——有真实案例：某团队离开 Next.js 改了 1200+ 文件、加了 2 万行代码、动了 3 个仓库；2026 年 1 月再次迁移到 TanStack Start 才把本地加载从 10–12 秒降到 2–3 秒
3. 需前后端分离：AI 推理任务时间长，必须异步化，前端需要独立的进度轮询/流式接口
4. Vite 6 + React 19 兼容性已验证，构建 <2s，可部署到任意静态托管
5. **Next.js 16 需要 Node.js 20.9+**；`middleware.ts` 已更名 `proxy.ts`（旧名弃用），`params`/`cookies()`/`headers()` 必须 await

⚠️ **CRA 已正式停止维护**（最后版本 2022 年，webpack 依赖树有未修复的 CVE），**新项目不要用**。

> 参考：某实测数据 Next 面板首屏 568ms vs SPA 1312ms（Slow 4G），但这是**为无人索引的页面付 TTFB + Node 运行时 + 缓存层的调试成本**。工作台不划算。

#### 后端：FastAPI vs NestJS

| 维度 | FastAPI | NestJS |
|---|---|---|
| 语言 | Python | TypeScript |
| 异步 IO | 原生 async，天然适配 AI API 调用 | 事件循环，适配但生态偏 CPU 密集 |
| AI 生态 | **LangChain / LlamaIndex / Replicate SDK / ComfyUI API / transformers 全在 Python 侧** | 需跨语言调 Python 服务 |
| 类型契约 | Pydantic → OpenAPI 自动生成，前端可直接生成 client | 强类型，端到端共享 |
| 性能 | CPU 密集任务弱 | 更好 |
| 招聘 | AI 方向 Python 更宽 | 前端转全栈更容易 |

**推荐 FastAPI。理由**：
1. **系统的主要复杂度在 AI 编排**，Python 生态是决定性优势（Replicate 跑 LoRA、ComfyUI 调 Vidu、transformers 做内容理解）
2. 任务队列天然多语言（Python 跑 AI worker，Node 跑前端 BFF）
3. Pydantic 生成的 OpenAPI 文档可让前端自动生成 client，无需手写胶水
4. `worker/process_video.py`、`scripts/train_lora.py` 这类胶水脚本能用同一语言

> **如果团队是纯 TypeScript 团队**，NestJS 也完全可行——只需把 AI 调用封装成独立 Python 微服务。**技术选型服务于人和业务，不是追框架热度。**

#### 任务队列：BullMQ / arq / Temporal / Airflow

| 工具 | 定位 | 用它 when | 别用它 when |
|---|---|---|---|
| **arq / RQ**（Python 侧） | 轻量 Redis 任务队列 | 单步任务、失败重试够用 | 多步流程需从崩溃处精确恢复 |
| **BullMQ**（Node 侧） | Redis 分布式任务队列，内置限流/去重/延迟 | 已有 Redis；多语言 worker 池；自建基础设施 | 架构无法运维 Redis；**需要持久化长流程** |
| **Temporal** | 持久化执行引擎，事件历史回放恢复 | **多步流程必须跨崩溃/部署存活**；跨服务语言协调；需暂停等待人工输入；AI Agent 工具执行管线 | 不想要自建运维；需要高吞吐 pub/sub；**简单后台任务** |
| **Airflow** | 批处理 DAG 调度 | ETL/ELT 批处理；与 dbt/Snowflake 集成 | **交互式任务队列；**跨进程重启的持久状态 |

**本系统的关键约束**：AI 视频生成一条可能 3–15 分钟，且**必须持久化进度**（不能因为 worker 重启就丢掉已付费的生成结果）。

**分阶段推荐**：
- **MVP 阶段**：`Redis + arq`（Python 原生，Redis 已有）。够用、运维成本低。
- **规模化后**：升级 `Temporal`。理由 —— AI 内容生产天然是**多步 saga**：选题→文案→审核→生图→审核→生视频→拼接→发布，其中任何一步都可能失败、超时、需要人工介入。Temporal 的**每步结果持久化 + 回放恢复**正好匹配。且它支持"工作流暂停等待人工输入数天"——**这对"人工审核后再继续生成"的业务流是刚需**。

> ⚠️ **Temporal 的代价**：工作流代码必须**确定性**（不能在里面读时钟、调网络，这些要放进 activity）；变更需用 SDK 的 patching API 做版本化，否则正在运行的旧实例会报非确定性错误；历史有硬上限（5 万事件 / 50MB / 实例），长循环需要 `Continue-As-New`；**新工程师需要约一周上手**。自建需运维 Temporal Server + 持久化存储（Cassandra/Postgres）+ 可选 Elasticsearch。**这部分投入要算进排期。**

> **Airflow 不适合本项目**：它是数据管道调度器，无持久化状态语义，交互式任务队列是反模式。

#### 数据库：SQLite / Postgres

| 维度 | SQLite | PostgreSQL 16 |
|---|---|---|
| 部署 | 零运维，文件即数据库 | 需服务，但生态成熟（托管选项众多） |
| 并发写 | ❌ 单写者 | ✅ MVCC 高并发 |
| JSON 字段 | 弱（BLOB 存储） | ✅ `jsonb` + GIN 索引（本系统大量存 AI 生成元数据） |
| 全文检索 | FTS5，中文分词需外接 | ✅ tsvector + 中文分词扩展 |
| 向量检索 | 需扩展 | ✅ **pgvector**（笔记内容/风格向量相似检索，竞品分析必备） |
| 并查 | ❌ | ✅ (row-level security) |
| 适用 | 本地开发、单人 | **生产** |

**推荐 Postgres 16。理由**：
1. AI 生成元数据（模型、参数、seed、prompt、参考图 ID）本质是半结构化 → `jsonb` 完美匹配
2. **pgvector 是竞品分析/内容推荐的基础设施**（"找和这条笔记风格相似的爆款"）
3. 多账号/多租户场景需要并发读
4. 本地开发用 Docker 起 Postgres 即可，SQLite 的"零运维"优势在有 Docker 后不成立

> 折中：本地开发 SQLite、线上 Postgres 会有类型差异（jsonb、数组），**不推荐**，会浪费大量调试时间。

#### 对象存储

**推荐 腾讯云 COS**（或阿里云 OSS）。

理由：① 用户的图片/视频必须放在国内（境外 CDN 访问慢，且有合规考量）；② 需要 CDN 加速直出；③ 需要预签名 URL 临时授权（给第三方 AI 服务读取参考图）；④ 需要生命周期规则（清理历史生成图）。

> ⚠️ **AI 服务的输入必须是公网可访问的 URL**。reAPI 等网关明确说明「不接受 base64 图片，只接受公网 HTTP(S) 媒体 URL」。这意味着**对象存储是硬依赖，不是可选优化**。Seedance 等火山引擎服务同样需要公网 URL。

**关键工程点**：
- 生成任务只传 URL，不传 bytes
- 内容审核失败的图片不计入计费，但要清理
- 参考图要能被 AI 服务读取 → 用预签名 URL 限时授权（不要设永久公开读）

#### AI 网关抽象层（最容易被忽略、也最重要）

**这是必须自建的一层**。理由：
- 可灵 API 已宣布 2026-09-15 下线一批模型 ID；Seedance 折扣 10-07 到期；Seedream 版本从 4.0→4.5→5.0 迭代。**模型 ID 硬编码 = 未来必然返工**
- 计价方式在不同云厂商间差异巨大（按张 / 按 token / 按秒 / 按分辨率档），需要统一成本核算
- 多 provider 需要故障转移和重试策略
- 成本可观测性（每次生成花了多少钱）只能自己做

**设计要点**：
```python
class ImageProvider(Protocol):
    async def generate(
        self, prompt: str, *,
        ref_images: list[str],   # 公网 URL，不是 base64
        aspect_ratio: str,       # "3:4" for 小红书
        seed: int | None,
        model: str,              # 配置化，不硬编码
    ) -> ImageResult: ...

# model ID 放配置：seedream-4.5 / seedream-5.0 / gemini-3-pro-image / ...
# 每次生成记录：provider, model, tokens/seconds, cost_cny, seed, prompt_hash
```

**必须记录的成本字段**：provider、model、输入模态、token/秒数、**折算人民币成本**、seed、prompt 版本、参考图 ID、是否审核失败。**没有成本可观测性，月底账单会让你无法归因。**

### E.4 MVP 与演进路线

**MVP（0-3 个月，1-2 人）**
- Vite+React / FastAPI / Postgres / Redis+arq / COS
- 2 个生图 provider（Seedream 主 + Nano Banana Pro 出图内文字）
- 1 个生视频 provider（Seedance 2.0-mini 或 Vidu Q3-turbo）

**阶段 2（3-6 个月）**
- 加 LoRA 训练流水线（Replicate）
- 加成本看板
- 加合规自检清单 + 敏感词检查
- 竞品数据源接入（采购千瓜/新红 API）
- 引入 Temporal 处理多步 saga + 人工审核暂停

**阶段 3（6 个月+）**
- 本地 Chrome 扩展（半自动填表，发布仍由人点）
- 账号矩阵的人设/内容差异化管理
- 风格向量检索（pgvector）

## G. 给架构师的三条硬约束（摘要复述）

1. **发布环节必须人机协作**。2026-03-10 薯管家公告明确将"主页所有公开笔记均为 AI 托管代发"列为**封禁**项。系统不要试图绕过它——绕不过去（事后聚类 + 行为指纹 + 内容相似度三层信号），且不值得。
2. **必须自建 AI Provider 抽象层**。可灵 9/15 批量下线模型、Seedance 折扣 10/7 到期、Seedream 持续迭代——模型 ID 硬编码等于给自己埋雷。同时它是成本归因的唯一手段。
3. **不要自研小红书爬虫作为核心能力**。签名对抗是持续投入的无底洞，账号风险直接传导客户资产。**版权案例已经存在**（2024 年小红书加密算法破解案判刑三年）。**把预算投在第三方数据采购上。**
