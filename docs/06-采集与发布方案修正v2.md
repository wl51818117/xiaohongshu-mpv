## 一、方案转向（关键）

| 维度 | v1 方案（作废） | **v2 方案（本篇）** |
|---|---|---|
| 选题来源 | 第三方数据平台付费 API（千瓜/新红）| **RSS 源 + 新闻源 + 公开榜单** |
| 是否碰小红书数据 | 买竞品笔记数据 | **完全不碰** |
| 发布方式 | Playwright 半自动预填 | **内置浏览器 + Web 端登录态复用** |
| 采集合规风险 | 低（买数据）| **极低（公开 RSS，无判例风险）** |

**这次转向实际上把最大的两个法律风险都消掉了**：
- 采集侧：不碰小红书数据 → 绕开了「判刑三年」「判赔 110 万」的全部风险
- 发布侧：用真实浏览器 Web 端 + 人工确认 → 不属于「AI 托管账号」

## 二、M1 采集中心重新设计：RSS / 新闻源路线

### 2.1 为什么 RSS 路线更适合

| 维度 | RSS/新闻源 | 第三方小红书数据平台 |
|---|---|---|
| 法律风险 | **无**（公开订阅源）| 低-中（数据权属争议）|
| 成本 | **接近零** | ¥1599-2599/月起 |
| 稳定性 | 高（源稳定）| 依赖厂商，价格口径混乱 |
| 内容质量 | 原始信息源，**有信息增量** | 已加工的爆款结论 |
| 独特优势 | **可以做跨平台选题搬运** | 只有小红书视角 |

**关键洞察**：RSS 源的独特价值是**信息增量**——它给你的是「发生了什么」，而小红书数据平台给你的是「别人怎么写的」。**前者是源头，后者是二手。** 做内容工作台，源头信息更有价值。

### 2.2 RSS 源分类清单（按可用性排序）

| 类别 | 具体源 | 能拿到什么 | 抓取方式 |
|---|---|---|---|
| **科技/AI 资讯** | 机器之心、量子位、36氪、虎嗅、InfoQ | 新技术、新产品、行业动向 | RSS 直接订阅 |
| **综合新闻** | 澎湃、财新、界面、第一财经 | 热点话题、社会事件 | RSS / 官网 |
| **垂直行业**（按你赛道选）| 母婴/美妆/家居/内衣行业媒体 | 品类动态、季节趋势 | RSS / 公众号 |
| **海外趋势** | Hacker News、TechCrunch、The Verge | 前沿概念、先进做法 | RSS（英文，需 AI 翻译）|
| **平台官方** | 抖音/快手/微信开放平台公告 | 规则变化、新功能 | 官方 RSS / 邮件订阅 |
| **聚合服务** | RSSHub（自建）、Feedly、Inoreader | 一站式聚合，可自建 | 自建 RSSHub 最重要 |

**⭐ 最推荐：自建 RSSHub**
- 开源项目：`DIYgod/RSSHub`（GitHub 高星）
- 价值：把**没有官方 RSS 的网站**变成有RSS（大量内容站都支持）
- 部署：Docker 一条命令
- 可覆盖：小红书站内外的各种内容源（但我们只用它抓**非小红书**的源）

### 2.3 RSS 库选型（Python 生态，已验证）

| 库 | Star | 特点 |
|---|---|---|
| **`feedparser`** | 2.4k | **Python 首选**，解析 RSS/Atom/JSON 全格式，容错好 |
| `gofeed` | 2.9k | Go 生态最好 |
| `node-feedparser` | 2.0k | Node 生态 |
| `feedjira` | 2.1k | Ruby |

**选 `feedparser`**。后端已定 FastAPI，Python 生态是决定性优势。

### 2.4 采集链路设计

```
RSS 源列表（配置化，可增删）
   ↓定时抓取（建议每 30-60 分钟）
feedparser 解析
   ↓
正文清洗（去 HTML 标签、提取摘要、压缩）
   ↓ 去重（SimHash / URL hash）
candidate_topics 入库
   ↓
【AI 选题转换】← 关键环节，见下
topics（可执行选题）
```

**字段设计**：

| 字段 | 说明 |
|---|---|
| `source_id` | 源标识 |
| `title` | 原始标题 |
| `url` | 原文链接（**必须保留，用于溯源和引用**）|
| `published_at` | 发布时间 |
| `raw_summary` | 原始摘要/正文片段 |
| `author` | 作者/机构 |
| `category` | 分类 |
| `simhash` | 去重用 |
| `raw_material` | 留档：AI 生成时作为事实来源 |

### 2.5 【关键环节】AI 选题转换

RSS 给的是原始资讯，不能直接当小红书选题。必须经过一层转换：

```
RSS 原文 → AI 读取 → 小红书化改造 → 可执行选题
```

**转换的四条规则**（写进 skill）：

| 规则 | 说明 | 反例 |
|---|---|---|
| **换视角** | 从「行业新闻」变成「用户关心的问题」| ❌「某品牌发布新品」→ ✅「新品到底值不值得买」|
| **落到具体人群** | 明确「谁会看」| ❌「行业趋势分析」→ ✅「上班族能用上的 3 个变化」|
| **给信息增量** | 加上原文没有的实操步骤/对比/避坑| ❌ 复述新闻 → ✅ 新闻+「你该怎么做」|
| **合规过筛** | 剔除涉及政治、医疗、金融荐股、法律建议等高风险题材 | — |

**⚠️ 高风险题材黑名单**（小红书对以下内容极严）：
- 医疗健康功效宣称、药品、医疗器械
- 金融投资荐股、理财承诺
- 法律纠纷维权（易触发「虚假诉讼」判定）
- 政治敏感、社会事件评论
- 减肥美药品效（「美白丸」「医美级」已明确违规）

→ **M1 层就要把这些源过滤掉**，不要等生成阶段才发现。

### 2.6 跨平台选题搬运（RSS 路线的独有优势）

同一个热点，别的平台已经在讨论了。可抓取：

| 平台 | 方式 | 注意 |
|---|---|---|
| 知乎 | RSSHub / 热门回答 | 抓问题标题做选题 |
| 抖音/快手热榜 | 官方热榜接口 / 第三方榜单 | 热度高但要与账号调性匹配 |
| B站热门 | RSSHub / 官方 | 适合知识类 |
| 微博热搜 | 公开榜单 | 时效性强，需快筛 |
| 微信公众号 | `wewe-rss`（需微信读书账号）或搜狗 | ⚠️ 版权风险，只取标题做选题 |

**合规要点**：只取**标题/话题方向**做二次创作，**不搬运原文和图片**。图片一律用 AI 重生或合规图库（Unsplash/Pexels），避免著作权。

## 三、M6 发布代理重新设计：内置浏览器 Web 端路线

### 3.1 王哥的思路是对的，而且有成熟方案可复用

「通过内置的 web 端登录再发布」——**这条路技术上完全可行，而且已有 2k star 的成熟项目验证过。**

### 3.2 ⭐ 首选方案：xhs_ai_publisher（强烈推荐复用）

| 项 | 信息 |
|---|---|
| 仓库 | `BetaStreetOmnis/xhs_ai_publisher` |
| Star | **2,089**（活跃，2026-10-03 仍在更新）|
| 许可证 | **Apache 2.0**（可商用，友好）|
| 技术栈 | Python + FastAPI + Playwright + PyQt5 |
| 部署 | Docker Compose（Web/API 模式）|

**它的核心机制（已读源码确认，与我们的设想高度吻合）**：

```
① 首次：可视化环境登录一次
   python scripts/xhs_login_cli.py --phone 138xxx --country-code +86
   ↓ 保存 storage_state + cookies到 ~/.xhs_system/
   ↓ 遇验证码/扫码/滑块 → 人工在浏览器里完成
   ↓ 登录态失效时自动扫描系统 Chrome Profile 导入

② 之后：Docker 无头复用登录态发布
   docker compose up -d   # 挂载登录态目录
   ↓ FastAPI + Playwright 无头执行发布
```

**关键设计（和我们方案完全兼容）**：
- 登录态与浏览器环境**按用户隔离**
- **默认禁用** JS 强制点击/强制 input 兜底（`XHS_ENABLE_FORCE_DOM_ACTIONS` 默认 false）→ 天然是「保守模式」
- 命中风控时**明确提示需要人工登录**，不硬刚
- 支持「手动确认模式」

### 3.3 其他候选方案对比

| 项目 | Star | 语言 | 特点 | 适用判断 |
|---|---|---|---|---|
| **`xhs_ai_publisher`** | 2,089 | Python | FastAPI+Playwright，登录态复用，Apache-2.0 | ★★★★★ **主推** |

| `creatorhub` | 2,204 | Python | 多平台内容监控采集面板 | 参考采集架构 |
| `oba-live-tool` | 1,701 | TS/Electron | 直播带货工具 | 场景不符 |
| `xhs_content_agent` | 311 | Python | LLM 采集+分析+生成+发布 | 参考流程设计 |

**注意**：`xhs_content_agent`、`xiaohongshu` 等项目的 readme 里说「Playwright 爬取小红书热门内容」——**这部分我们不用**，只借鉴它们的发布与生成环节。

### 3.4 ⭐ 重要发现：Agent Skill 形态已经有人做对了

`DeliciousBuding/xiaohongshu-skill`（43 star）的描述值得注意：

> "Xiaohongshu & RedNote skill for AI agents — search, read notes, publish, and run **approval-gated automation** with Python Playwright and clean JSON output."

**「approval-gated automation」+「clean JSON output」** —— 这正是我们要的形态：
- 工具返回结构化 JSON，可被 Agent 直接消费
- 发布动作走**审批闸门**，人工放行才执行

**这个形态可以直接对上我们的 harness 内核**：
```
dsh 内核的 approval 机制 ←→ skill 的 approval-gated
d-sh 的 ctx.tools.register ←→ skill 的 clean JSON output
```

→ **所以我们的 `xhs_*` 工具可以直接借鉴这个 skill 的工具定义与输出契约设计。**

### 3.5 我们的集成方案（推荐路线）

```
┌─ 工作台后端（FastAPI）
│   └─ 发布服务层
│      ├─ 方案A（主）：Docker 跑 xhs_ai_publisher
│      │    · 首次人工登录（可视化浏览器，扫码）
│      │    · 登录态存盘，挂载到容器
│      │    · 调用其 REST API 执行发布
│      │    · 或直接复用其源码作为我们的发布服务
│      │
│      └─ 方案B（备）：自建 Playwright 代理
│           · 借鉴 xhs_ai_publisher 的登录态管理方案
│           · 但发布前停下，等人点确认
```

**必须坚持的三条**：

| # | 规则 | 理由 |
|---|---|---|
| 1 | **登录必须人工完成** | 扫码/验证码/滑块是真人验证，程序过不去也不该过 |
| 2 | **发布前必须有预览确认** | 不可逆动作，人工把关 |
| 3 | **不做全自动无人值守** | 平台 2026 明确封禁 AI 托管账号 |

### 3.6 Web 端发布的实际可行性（为什么这条路能走通）

小红书创作者中心有**完整的 Web 端发布页**：`creator.xiaohongshu.com/publish/publish`
- 支持图文上传、标题正文、标签、封面裁剪
- 支持视频上传
- 即：`media-auto-publisher` 这个 skill 明确列了「小红书 creator.xiaohongshu.com」为支持的发布页面

**所以 Web 端功能是完整的**，不需要逆向 App 协议。

⚠️ **但要注意**：
- Web 端发布通常**不支持**部分移动端功能（如 Live Photo、部分 POI 玩法）
- Web 端发布的风控判定是否与移动端一致，**需要小号实测**
- 部分类目可能强制要求 App 内发布

## 四、⭐ 图文素材：发现一个 7k star 的现成方案

### 4.1 guizang-social-card-skill

| 项 | 信息 |
|---|---|
| 仓库 | `op7418/guizang-social-card-skill` |
| Star | **7,337**（2026-10-03 仍在更新）|
| 许可证 | ⚠️ **AGPL-3.0**（有商用限制，见下）|
| 做什么 | 从文章/文案/截图/视频生成**小红书图文组图** |

**技术路线（对我们极其友好）**：
```
单文件 HTML + CSS → Playwright 截图 → PNG
```
**为什么这个路线好**：
- HTML/CSS 是文本 → **Agent（harness 内核）能直接写、读、改**
- 版式精确可控（CSS Grid + 严格字号/留白）
- **不需要前端构建链**，`node render.mjs` 直接出图
- 内置 Playwright 校验脚本（9 条规则，真实 DOM 测量）

**规格正好匹配小红书**：
- `.poster.xhs` = **1080×1440（3:4）** ← 小红书标准尺寸
- 28 个版式骨架 + 10 套主题预设
- 校验脚本检查溢出/字号下限/footer碰撞

### 4.2 ⚠️ 许可证是硬约束（必须注意）

**AGPL-3.0 的三条硬性要求**：
1. 必须保留版权声明
2. **衍生品必须开源**（任何修改/Fork/二次分发需以 AGPL-3.0 公开完整源码）
3. **网络服务也要开源** —— 即使只是部署成 SaaS 给别人用，不分发代码也要公开源码

**我们的两种应对**：

| 用法 | 是否可行 | 说明 |
|---|---|---|
| **直接调用**（不修改，作为独立工具跑） | 🟢 可行 | 保留版权声明即可，不构成分发衍生品 |
| **Fork 并修改后自用** | 🟡 可行但**必须开源** | 内部使用不构成分发；但若对外提供服务则需开源 |
| **把它的代码集成进闭源商业产品** | 🔴 **不可行** | 违反 AGPL 第3 条 |

**建议**：
- MVP 阶段**作为独立工具调用**（它本来就是个 Agent skill，直接放进 harness 的技能目录）
- 若要改造其源码并闭源，**不要 Fork**，而是**参考其设计思路自建**
- 保留 `LICENSE` 与版权声明

### 4.3 图文素材的双路方案

```
                  ┌─ 路径1：AI 生图（Seedream/ImageGen）
                  │   适合：实拍感、场景图、对比图、人物图
素材生成 ─────────┤
                  └─ 路径2：HTML 卡片渲染（guizang skill）
                      适合：干货合集图、数据图表、教程分页、方法论
```

**这是互补而非替代关系**：
- 干货类内容（图表/清单/方法论）→ 卡片渲染**又快又准又可控**
- 实拍/场景/人物类→ AI 生图

**建议**：图文链路**两条都做**，卡片渲染作为主力（性价比高、版式可控），AI 生图补充。

## 五、修订后的完整链路

```
RSS 源/新闻源（feedparser）
   ↓ 定时抓取 + 去重
原始资讯库
   ↓ AI 选题转换（换视角/落人群/给增量/合规过筛）
选题库 topics（带关键词、竞争度、来源溯源）
   ↓ 占用建稿
文案工坊（AI 生成 + 去 AI 味 + 合规校验）
   ↓
   ├─ 图文：HTML 卡片渲染（主力）+ AI 生图（补充）
   └─ 视频：首帧图 → 图生视频 → ffmpeg 拼接
   ↓
组合发布包（AI 声明必填）
   ↓
半自动发布（xhs_ai_publisher 复用登录态，人工确认点发布）
   ↓
数据回流 → 爆文要素 → 回流选题库
```
